# Generated and Vendored Code

<!-- STANDARD: 3min -- excluding machine-written code, and verifying the exclusion applies -->

## Why exclusion matters more than it looks

A gate that flags files nobody wrote and nobody may edit produces noise. Noise is not neutral — it trains everyone to ignore the check. That is the mechanism by which a linting gate gets disabled, and it usually starts with a generated file.

This is R6: exclude generated, vendored and build output explicitly, and **verify** the exclusion.

## What must be excluded

| Category | Examples | Why |
|---|---|---|
| **Generated source** | ORM model files, protobuf stubs, GraphQL types, OpenAPI clients | machine-written; the generator is the source of truth |
| **Vendored dependencies** | `vendor/`, `third_party/`, a copied upstream library | not yours to format; upstream's formatting is correct for it |
| **Build output** | `dist/`, `build/`, `out/`, `.next/`, compiled artefacts | regenerated; never edited |
| **Minified assets** | `*.min.js`, `*.min.css` | one line by construction; the linter would report everything |
| **Lockfiles** | `package-lock.json`, `Cargo.lock`, `go.sum`, `Podfile.lock` | generated; a diff here is a dependency change, not a style change |
| **Snapshots** | `__snapshots__/`, golden files | **careful** — see the caveat below |
| **Migration files** | database migrations already applied | altering them breaks the migration record |
| **Third-party fixtures** | captured HTTP responses, large test data | usually machine-produced and often intentionally odd |

## The golden-file caveat

A golden or snapshot file may be **excluded legitimately or not** — it depends on whether the formatter is part of what is being asserted.

| Situation | Correct treatment |
|---|---|
| Golden files produced by the formatter itself | **exclude** — formatting them changes the assertion |
| Snapshot tests of a data structure | **include** — the snapshot should follow the standard |
| Generated code that is also read by humans | **include**, if it is hand-maintained after generation |
| A vendored snapshot of an upstream file | **exclude** — its bytes are the point |

**The rule:** exclude a file when its exact bytes are the assertion, or when it is not yours to change. Do not exclude a file merely because it is inconvenient — that is how a real source file escapes the standard.

## Exclusion mechanisms, per tool

| Tool | Mechanism |
|---|---|
| Prettier | `.prettierignore` |
| Biome | `files.ignore` in `biome.json` (or the vcs-aware `includes` config) |
| ESLint | `ignores` in the flat config |
| swiftlint | `excluded:` in `.swiftlint.yml` |
| ktlint / detekt | `excluded` / `excludes` in the config |
| ruff | `exclude` / `extend-exclude` in `pyproject.toml` |
| golangci-lint | `issues.exclude-dirs` |
| clang-format | `.clang-format-ignore` |
| shellcheck | `# shellcheck disable` per file, or a wrapper script that filters |
| generic | a path glob in the CI job |

## The header marker

Where the tool has no ignore file, or where you want the reason to travel with the file, mark it in the header:

```go
// Code generated by sqlc. DO NOT EDIT.
package db
```

```python
# This file is generated by the schema tool. Do not edit by hand.
```

The convention is old and widely recognised: **"Code generated … DO NOT EDIT."** Several tools understand it automatically (Go tooling, some linters), and every human does.

**Two benefits over a path glob:** the marker survives a file moving, and it carries the reason rather than requiring a lookup in a config.

## Verifying the exclusion actually applies

A configured exclusion that does not take effect is worse than none, because the intent is recorded and the noise remains.

```bash
# 1. Generate or touch a file in an excluded path.
touch vendor/example/pkg/thing.py

# 2. Run the formatter's CHECK mode (not its fix mode).
make fmt-check
#    → must pass. If it reports vendored/example/pkg/thing.py, the exclusion is not applied.

# 3. Run the linter over the whole tree.
make lint
#    → must not name any file in an excluded directory.

# 4. Confirm the path is matched by the config's own pattern.
#    (a glob that looks right but does not match is the common defect)
```

Step 4 is the one that catches the frequent case: a pattern like `build/` that does not match `**/build/`, or a directory that was renamed after the exclusion was written.

## The common misconfigurations

| Misconfiguration | Symptom | Fix |
|---|---|---|
| Exclusion written for a directory that does not exist yet | generated files appear once the generator runs | verify with an actual generated file, not a hypothetical |
| Pattern matches the root only | nested build directories are still linted | use the `**/` form where the tool supports it |
| Exclusion added to the linter but not the formatter | the formatter reformats vendored code | configure **both**, and check both |
| A generated file is hand-edited once | it now contains human code and drifts from the generator | regenerate, or remove it from generation and own it |
| The generator's output goes to a tracked path | a generated diff appears in every PR | generate into an ignored path, or commit deliberately with a marker |
| A new generator is added and nobody excludes its output | noise appears weeks later | the code-review checklist includes "does this add generated output?" |

## Generated code and the format check

An important asymmetry: even for generated code that is **committed**, it must be either formatted *by the generator* or excluded.

```text
Committed generated output — two correct options:
  A. The generator formats its output (preferred)
     → the generated files pass the check like anything else
  B. The files are excluded, with a header marker and a reason
     → they are visibly outside the standard

There is no third option where generated files are committed, unformatted, and in scope.
That combination produces a permanently failing gate or a permanently suppressed rule.
```

**Option A is better** because it keeps the codebase uniform and removes the need to reason about scope. It requires the generator to be configurable — usually it is.

## Checklist

- [ ] Generated source, vendored code, build output, minified assets and lockfiles are all excluded (R6)
- [ ] Golden and snapshot files are classified deliberately, not blanket-excluded
- [ ] Every exclusion carries a reason in the config
- [ ] Header markers are used where the reason should travel with the file
- [ ] Both the formatter **and** the linter exclude the same paths
- [ ] The exclusion has been verified with an actual generated file, not assumed
- [ ] The pattern form is correct for the tool (root versus nested directories)
- [ ] Committed generated output is either formatted by the generator or excluded
- [ ] Adding a generator includes adding its output to the exclusion policy
