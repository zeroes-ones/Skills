## How to run everything

```bash
cd skills/14-finance/options-trading-playbook
export PYTHONIOENCODING=utf-8          # Windows: the tool prints non-ASCII glyphs
```

`python3` is not on PATH here. Use `py -3` on Windows, `python3` elsewhere.

```bash
# Card 1: a positive corner
py -3 scripts/payoff_check.py --tp 2.5 --sl 1.0 --p 0.35 --cost-r 0.02

# Card 2: negative at the win rate the card predicts
py -3 scripts/payoff_check.py --tp 0.5 --sl 2.0 --p 0.70

# Card 2 as written, at its break-even win rate: EXACTLY ZERO
py -3 scripts/payoff_check.py --credit 1.00 --width 5.00 \
    --tp-money 50 --sl-money 200 --p 0.80

# Card 7: the multi-rung fee threshold
py -3 scripts/payoff_check.py --scaling-check --legs 4 \
    --fee-per-contract 0.65 --rung-split 3 --position-value 5.00

# Card 3 at a conservative p: marginal, and why
py -3 scripts/payoff_check.py --tp 0.5 --sl 1.0 --p 0.68

# Card 6: the fee exceeds the edge
py -3 scripts/payoff_check.py --tp 2.5 --sl 1.0 --p 0.35 \
    --fee-per-contract 0.65 --legs 4 --r-dollars 15

# the log modes
py -3 scripts/payoff_check.py --from-log examples/logs/synthetic-options-log.csv
py -3 scripts/payoff_check.py --from-log examples/logs/synthetic-options-log.csv \
    --setup debit-spread-2.5R --tp 2.5 --sl 1.0 --p 0.35
```

`bash scripts/verify-skill.sh` runs every one of these, asserts the documented values,
and re-runs each twice to prove the output is byte-identical.

## The log schema

`--from-log` reads the **same CSV schema as the sibling engines** in
`timeframe-performance-statistics` and `edge-and-payoff-engineering`:

```
trade_id,open_date,close_date,pnl,risk[,cost][,setup][,symbol][,dte][,iv_rank][,side]
```

| Column | Required | Meaning |
|---|---|---|
| `trade_id` | yes | row identifier |
| `open_date` | yes | ISO `YYYY-MM-DD` |
| `close_date` | yes | ISO `YYYY-MM-DD`; the date the trade belongs to |
| `pnl` | yes | realised P&L of one CLOSED trade; may be negative or zero |
| `risk` | optional but expected | the planned per-trade risk unit. If present and positive on every row, the engine runs in **R MODE** (`r_i = pnl_i / risk_i`); otherwise it runs in **CURRENCY MODE** and says so loudly |
| `cost` | optional | commission + fees + half-spread for that trade. Absent → 0, and the engine warns that every result is flattering at zero cost |
| `setup` | optional but expected | the **cohort tag**. This is the key that makes `--setup` filtering and the proposed-vs-realised comparison possible |
| `symbol`, `dte`, `iv_rank`, `side` | optional | carried through, not used in the arithmetic |

Two conventions, inherited rather than invented:

- **Break-even trades (`pnl = 0`) are counted in `n`, contribute 0 to the
  expectancy, and are EXCLUDED from the win-rate denominator**: `p = wins / (wins +
  losses)`. This matches `timeframe-performance-statistics`.
- **A trade belongs to the bucket containing its close date, never its open date.**
  Same convention as `timeframe-performance-statistics`; the engine echoes it rather
  than re-deriving it.

Lines beginning with `#` are comments. A comment beginning `# PROVENANCE:` is
**echoed into the engine's own output**, so an output can never be separated from the
label of the data behind it.

## The SYNTHETIC log

`logs/synthetic-options-log.csv` is **SYNTHETIC / ILLUSTRATIVE**.

- It is **not market data**. It is **not a backtest**. It is **not a result**.
- It carries **no market information whatsoever** and must never be quoted as a
  finding about any instrument, strategy, volatility regime or period.
- It was invented by the skill author so that `--from-log` and the sibling cohort
  engines have a log whose arithmetic a reader can check on paper.
- It is generated by `logs/generate_synthetic_log.py` at **fixed seed
  `20261014`**, stdlib only, byte-identical on every run. Re-running the generator
  reproduces the CSV exactly; `verify-skill.sh` asserts this.
- The label appears in the generator, in the CSV header comments (and therefore in
  every engine output via the provenance echo), in this README, and in
  `run-output.txt`.

### What is in it

80 invented closed option positions across two invented cohorts, four invented
symbols, close dates 2025-01-15 .. 2025-06-27. `risk = 200.00` on every row, and
`cost` is an invented estimate at `$0.65` per contract per ticket.

| Cohort | Corner | n | wins | losses | `p` | `avg_win` | `avg_loss` | `b` | `E` gross | cost | `E_net` |
|---|---|---|---|---|---|---|---|---|---|---|---|
| `credit-condor-50-2x` | short premium, 50% / 2× | 40 | 31 | 9 | 0.7750 | 0.250R | 1.000R | 0.250 | −0.03125R | 0.0260R | **−0.05725R** |
| `debit-spread-2.5R` | long premium, 2.5R / 1R | 40 | 14 | 26 | 0.3500 | 2.470R | 1.000R | 2.470 | +0.21450R | 0.0130R | **+0.20150R** |

The two cohorts are deliberately chosen to sit on **opposite sides of the break-even
line** — one negative corner and one profitable corner. That contrast is the point of
the fixture, and it is what makes the cohort-attribution lesson in
`../references/from-negative-to-positive-walkthrough.md` demonstrable.

The debit cohort's wins are *not* all at exactly 2.5R: they exit between 2.18R and
2.70R, averaging exactly **2.4700R** (14 values summing to 34.58). That is what a real
scale-out or early exit looks like, and it makes the difference between the *planned*
`b = 2.5` and the *realised* `b = 2.47` visible in the output.

### Hand-check the fixture

Every value a reader needs is written in the CSV's own header comments. The arithmetic:

```
credit-condor-50-2x
  p          = 31 / 40                = 0.7750
  b          = 0.250 / 1.000          = 0.250
  E          = 0.7750 * 0.25 - 0.2250 = -0.03125 R
  cost_r     = 5.20 / 200             = 0.0260 R
  E_net      = -0.03125 - 0.0260      = -0.05725 R

debit-spread-2.5R
  p          = 14 / 40                = 0.3500
  avg_win    = 34.58 / 14             = 2.4700 R
  b          = 2.4700 / 1.0000        = 2.470
  E          = 0.3500 * 2.47 - 0.6500 = +0.21450 R
  cost_r     = 2.60 / 200             = 0.0130 R
  E_net      = +0.21450 - 0.0130      = +0.20150 R
```

## `--from-log --setup`: the proposed card against one cohort

This is the mode that scores a prediction.

```bash
py -3 scripts/payoff_check.py --from-log examples/logs/synthetic-options-log.csv \
    --setup debit-spread-2.5R --tp 2.5 --sl 1.0 --p 0.35
```

The comparison panel, verbatim:

```
==============================================================================
PROPOSED CARD vs REALISED
==============================================================================
  field              proposed     realised
  p                    0.3500       0.3500
  b                    2.5000       2.4700
  E                    0.2250       0.2145
  E_net                0.2050       0.2015
  sd                   1.6694       1.6551
```

The card predicted `p = 0.35` and the cohort delivered `p = 0.3500` — because this
synthetic fixture was built to do exactly that. **Do not read that agreement as
typical.** It is a property of the invented data, and on a real log the gap between
these two columns is the entire point of running the mode: a card is a prediction and
this is the score.

The `b` gap (`2.5000` planned versus `2.4700` realised) is the more instructive one.
It is small, it is real, and it exists because wins are taken slightly early. A
`b`-target that can only be hit perfectly is a `b`-target that is never hit.

## The credit-mode input

`--credit` and `--width` are quoted the way an option chain quotes them — **per
share**. `--tp-money` and `--sl-money` are **per spread**. `--multiplier` (default
100, the standard US equity-option contract size) reconciles the two:

```bash
py -3 scripts/payoff_check.py --credit 1.00 --width 5.00 \
    --tp-money 50 --sl-money 200 --p 0.80
```

```
R BASIS
  structural: 1R = the structure's max loss (W - C) x multiplier = 400.00

INPUTS
  credit          : 1.00 (per share)   width: 5.00 (per share)   multiplier: 100
  per spread      : credit 100.00   width 500.00   max loss (W-C): 400.00
  target          : 50.00 (50.00% of credit)   stop: 200.00 (2.00 x credit)
```

So `1R = $400`, the target is **50.00% of the credit**, the stop is **2.00 × the
credit**, and `b = 50/200 = 0.25`. The engine derives the `1R` basis and prints it,
rather than asking you to translate.

---

## The two R conventions, and why the tool prints which one it used

| Mode | `1R` is | `b` comes from |
|---|---|---|
| `--tp/--sl` | a numeraire; the loss is re-based to exactly 1R | `tp / sl` |
| `--credit/--width` | the structure's max loss `(W − C) × multiplier` | `tp_money / sl_money` |
| `--from-log` | the log's `risk` column | realised `avg_win / avg_loss` |

These agree when the stop sits at the structure's maximum loss, and differ when it
does not — which is the normal case for premium selling, where the stop is usually
far inside the max loss. The engine always prints an **`R BASIS`** line saying which
reading it used, and that line is the first thing to check when an output looks wrong.

The one term where the choice matters is cost: `c_R = cost_per_trade / R_dollars`. A
larger `R` makes the fee look smaller. Define `R` once, write it on the card, and use
it everywhere.

## What these examples do NOT do

- **They do not validate any strategy.** Every verdict is arithmetic on a stated
  prediction. None has been traded.
- **They do not use market data.** The only log is SYNTHETIC. The engine has no
  price series, no vendor feed, no network call and no third-party dependency.
- **They do not measure `p`.** A proposed `p` is a hypothesis; only a cycle can
  grade it. See `../references/the-iteration-protocol.md`.
- **They do not guarantee anything.** See
  `../references/what-this-cannot-promise.md` — read it before acting on any number
  in this directory.
